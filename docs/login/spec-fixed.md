# 로그인(auth/login) — 확정 요구사항 명세

**작성일**: 2026-08-09
**범위**: `/auth/login` 페이지 (이메일 로그인 + Google 간편 로그인)
**상태**: 요구사항 확정, 구현 전 단계
**참고**: [../auth/spec.md](../auth/spec.md)(회원가입 v3), [../routing.md](../routing.md)

---

## 1. 개요

`/auth/login`은 [docs/routing.md](../routing.md)에 정의된 인증 전용 독립 영역(`auth`)의 로그인 페이지다. 이메일/비밀번호 로그인과 Google OAuth 간편 로그인을 함께 제공한다. Google OAuth는 회원가입(`/auth/register`)에서 이번 페이지로 이관하기로 확정된 기능이며, 관련 코드(`google-auth-button.tsx`, `/api/auth/callback`, `shared/api/supabase/client.ts`)가 이미 구현·보존되어 있어 재사용한다.

## 2. 인증 방식

- **이메일 + 비밀번호**: Supabase Auth 기본 이메일 로그인
- **Google OAuth**: Supabase Auth의 Google Provider, 기존 회원가입 페이지에서 이관된 `GoogleAuthButton`을 이 페이지에 배치

## 3. 폼 필드 구성

| 필드     | 필수 여부 | 설명                                                                           |
| -------- | --------- | ------------------------------------------------------------------------------ |
| 이메일   | 필수      | Supabase Auth 계정 식별자                                                      |
| 비밀번호 | 필수      | 별도 형식 검증 없음 (빈 값만 아니면 서버로 전송, 실제 일치 여부는 서버가 판단) |

**검증 모드**: `onBlur` (기존 `useAppForm` 기본값 그대로 사용). 로그인은 이미 정해진 값을 입력하는 행위라 타이핑 중 실시간 피드백이 불필요하며, 회원가입처럼 형식 자체를 사용자가 그 자리에서 맞춰나가야 하는 시나리오가 아니다.

## 4. 세션 유지

- httpOnly 쿠키 기반, Supabase 기본 세션 refresh 메커니즘을 그대로 사용한다.
- 브라우저를 닫아도 로그인 상태가 자동으로 유지된다("로그인 상태 유지" 체크박스 같은 선택적 UI를 별도로 두지 않는다).
- 회원가입 spec.md와 동일하게 BFF(Route Handler)가 Supabase 서버 SDK를 통해 세션을 관리하고, 클라이언트는 Route Handler만 호출한다(단, Google OAuth 리다이렉트 트리거는 브라우저 Supabase 클라이언트가 필요 — 기존 결정 그대로 유지).

## 5. 에러 처리

- **이메일/비밀번호 로그인 실패**(이메일 미가입, 비밀번호 틀림 모두 포함): **구분 없이 통일된 메시지**로 안내한다(예: "이메일 또는 비밀번호가 올바르지 않습니다"). 어느 쪽이 틀렸는지 알려주면 공격자가 가입 여부를 추론할 수 있는 보안 리스크를 차단하기 위함이다.
  - 참고: 회원가입(spec.md v3 §8)에서는 이메일 중복 시 "이미 가입된 이메일입니다"로 명확히 안내하는 반대 정책을 채택했다 — 가입은 존재 여부를 알려주는 게 UX상 자연스러운 반면, 로그인 실패는 계정 존재 여부를 추측하게 하는 공격 벡터가 되므로 통일 메시지가 원칙에 맞다.
- **이메일 미인증 상태**: 이메일/비밀번호 자체는 맞지만 Supabase 이메일 인증이 완료되지 않은 계정이 로그인을 시도하면, 로그인을 차단하고 기존 `/auth/verify-email` 페이지로 이동해 재안내한다(이 상태는 계정 존재가 이미 명백하므로 통일 메시지 원칙과 충돌하지 않음). 인증 메일 재발송 기능은 이번 스코프에 포함하지 않는다.
- 에러 메시지는 회원가입과 동일하게 `src/shared/api/error.ts`의 `ApiError` 클래스 및 `src/types/api.ts`의 `ApiErrorCode` 유니온 체계를 따른다.

## 6. 로그인 후 흐름

1. 이메일/비밀번호 입력(또는 Google 인증) → 로그인 성공
2. 홈(`/`)으로 이동

Google 로그인은 기존 `/api/auth/callback`의 리다이렉트 대상을 그대로 사용한다(현재 origin으로 리다이렉트 — 필요 시 이번 스코프에서 `/`로 명확히 조정).

## 7. 비밀번호 찾기 연결

- 로그인 폼에 "비밀번호를 잊으셨나요?" 링크를 배치한다.
- 링크는 `/auth/forgot-password`를 가리키되, 실제 페이지 구현은 이번 스코프가 아니다(routing.md에 경로만 정의되어 있음). 클릭 시 미구현 상태로 연결될 수 있다.

## 8. 회원가입 연결

- 로그인 폼 하단에 "아직 계정이 없으신가요? 회원가입" 형태로 `/auth/register` 링크를 배치한다.

## 9. 용어 정의 (Ubiquitous Language)

회원가입 spec.md와 동일한 용어를 사용한다.

| 용어        | 정의                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------ |
| 통일 메시지 | 이메일 미가입과 비밀번호 오류를 구분하지 않고 하나의 문구로 안내하는 에러 정책                                           |
| 세션 유지   | 브라우저 재실행/재방문 시에도 별도 재로그인 없이 로그인 상태가 유지되는 것. httpOnly 쿠키 + Supabase 세션 refresh로 구현 |

## 10. 향후 작업 (Out of Scope, 현 단계)

- Supabase MCP 연결 및 실제 로그인 연동 (이 spec은 요구사항 정의까지만 다룸)
- `/auth/forgot-password`, `/auth/reset-password` 실제 페이지 구현 — 링크만 배치
- 이메일 인증 메일 재발송 기능
- "로그인 상태 유지" 선택적 체크박스 — 항상 자동 유지로 고정
- 로그인 폼 실시간 검증(onChange) — onBlur로 고정
- Google 외 다른 OAuth Provider
- 리다이렉트 파라미터(`?redirect=`) 지원 — 로그인 성공 시 항상 홈(`/`)으로 고정
