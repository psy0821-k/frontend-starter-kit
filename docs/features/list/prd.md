# Features 메뉴 목록 페이지 PRD

**작성일**: 2026-08-11
**상위 문서**: [spec-fixed.md](./spec-fixed.md)

---

## 개요

`/features` 메뉴(routing.md 정의: 특정 페이지에 종속되지 않는 재사용 가능한 기능 모듈)의
목록 조회 페이지를 신규 작성한다. `/templates` 목록의 검색+카테고리 필터 UX를 참고하되,
데이터는 아직 DB 테이블이 없어 정적 하드코딩 목록으로 시작하고, 목록 순회 방식은
templates(무한스크롤)와 다르게 **페이지네이션**을 사용한다.

---

## 사용자 스토리

- 방문자로서, `/features`에 들어가면 이 플랫폼이 제공하는 기능 모듈 목록을 한눈에
  볼 수 있다.
- 방문자로서, 검색어를 입력해 원하는 기능을 이름/설명 기준으로 빠르게 찾을 수 있다.
- 방문자로서, 카테고리를 선택해 관심 있는 유형(예: search, board)만 걸러볼 수 있다.
- 방문자로서, 검색/필터 결과가 많으면 페이지를 넘겨가며 나머지 항목을 볼 수 있다.
- 방문자로서, 조건에 맞는 항목이 없으면 그 사실과 다음 행동(필터 초기화)을 안내받는다.

### 서버 컴포넌트 + URL searchParams 채택

**Context** — `/features` 목록은 검색어·카테고리·페이지 3가지 상태를 가져야 하고,
이미 `/templates`가 검색+카테고리를 URL(`searchParams`) 기반 서버 컴포넌트 패턴으로
구현해 검증된 선례가 있다. 새 상태(페이지네이션)를 추가할 때 기존 패턴을 따를지,
클라이언트 상태나 별도 스토어로 갈지 결정이 필요했다.

**Decision** — 안 B: `src/app/features/page.tsx`(서버 컴포넌트)가 `searchParams`에서
`category`/`q`/`page`를 읽어 `feature-catalog/model/`의 순수 함수(`filterByCategory`,
`filterBySearch`, `paginate`)로 필터링·페이지 슬라이싱까지 서버에서 계산한 뒤, 결과
배열만 클라이언트 카드 리스트 컴포넌트에 전달한다. 검색 입력·카테고리 필터·페이지네이션
컨트롤은 각각 얇은 클라이언트 컴포넌트로, `router.push`를 통해 URL만 갱신한다
(`StarterKitCategoryFilter`/`StarterKitSearchInput`과 동일 원리).

**Alternatives**

- 안 A(클라이언트 단일 페이지) — URL에 상태가 반영되지 않아 새로고침/링크 공유 시
  필터·페이지가 초기화된다. spec-fixed.md에서 이미 "templates의 searchParams 패턴과
  일관되게"라고 못박았으므로 이 요구를 충족하지 못해 기각.
- 안 C(Zustand 스토어) — CLAUDE.md가 "Zustand는 서버 상태를 담지 않음" 원칙을 명시한다.
  Feature 목록은 정적이라도 "서버에서 내려오는 데이터"로 취급하는 게 기존 관례(모든
  목록 데이터는 서버 컴포넌트가 조회)와 맞고, 필터/페이지 상태도 URL로 대체 가능해
  전역 스토어가 주는 이점이 없다. 오히려 이 페이지만을 위한 스토어가 새 패턴을
  만들어 일관성을 해치므로 기각.

**Consequences**

- 장점: 새로고침·URL 공유·뒤로가기가 모두 자연스럽게 동작한다. 필터/페이징 로직이
  순수 함수로 분리되어 `model/*.test.ts`에서 독립적으로 테스트 가능하다. templates와
  동일한 멘탈 모델이라 유지보수 시 두 도메인을 오갈 때 학습 비용이 없다.
- 단점: 페이지 전환마다 서버 컴포넌트가 재실행된다 — 데이터가 정적이라 비용은
  미미하지만, 클라이언트 상태 방식보다 페이지 전환 시 네트워크 요청(RSC 페치)이
  1회 추가로 발생한다. 컨트롤마다 URL 조립 로직이 조금씩 중복될 수 있어(카테고리
  필터, 검색 입력, 페이지네이션 각각 `URLSearchParams` 다룸) 필요 시 공통 헬퍼로
  추출을 고려해야 한다(단, 현재 2곳(templates, features)뿐이므로 이번엔 추출하지
  않고 "2회 규칙" 관찰 대상으로만 남긴다).

## Out of Scope

- 상세 페이지(`/features/[id]`)
- DB 연동(`features`/`feature_files` 테이블) — 이번엔 정적 데이터만
- 아이콘/태그 표시
- 관리자용 생성/수정/삭제
- 페이지네이션 컨트롤의 `shared/ui` 승격 (2회 규칙 미충족, 우선 도메인 내부에 둠)
- 무한스크롤 (의도적으로 페이지네이션 채택)
