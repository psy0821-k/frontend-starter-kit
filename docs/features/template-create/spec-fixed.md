# 템플릿 생성 기능 정의서 (Fixed)

## 개요

관리자가 템플릿(스타터 킷)을 등록할 수 있다. 등록된 템플릿은 `/templates/[id]` 상세 페이지에서 파일별 코드를 볼 수 있다.

## 용어 정의 (Ubiquitous Language)

| 용어                      | 정의                                                                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| 템플릿(Template)          | 등록 대상이 되는 자산 하나. 코드상 타입/폴더명은 `StarterKit`으로 남아 있으며 동일 개념이다.        |
| 템플릿 파일(TemplateFile) | 템플릿을 구성하는 코드 파일 하나. `file_path` + `code` + `language` + `sort_order`.                 |
| 카테고리(Category)        | 템플릿이 속한 프로젝트 유형 분류. 이번 spec에서는 `erp` / `포트폴리오` / `쇼핑몰` 3종으로 정의한다. |
| 관리자(Admin)             | 템플릿 등록/수정/삭제 권한을 가진 사용자. `requireAdmin` 가드로 판별한다.                           |

> 카테고리 값은 이번 문서 확정 사항이며, 실제 코드(`STARTER_KIT_CATEGORIES` 등)에 반영하는 작업은 다음 단계(PRD/구현)에서 진행한다. 이번 단계는 요구사항 문서만 대상으로 한다.

## Primary User

관리자(Admin) 전용 기능이다. 일반 사용자는 등록 화면에 접근할 수 없다(미권한 시 404).

## 최소 동작 시나리오

1. 관리자가 `/templates/new`에 접속해 템플릿 정보를 입력하고 "등록하기"를 누르면 템플릿이 생성되고 상세 페이지(`/templates/[id]`)로 이동한다.
2. 관리자가 코드 파일을 여러 개 추가해 등록하면, 상세 페이지에서 파일별로 구분되어 조회된다.
3. 관리자가 아닌 사용자가 `/templates/new`에 접속하면 404 페이지가 표시된다.

## 입력 필드

| 필드                          | 필수 여부                 | 형식                                       | 비고                                                                                                                   |
| ----------------------------- | ------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 제목(title)                   | 필수                      | 문자열, 최대 100자                         |                                                                                                                        |
| 한 줄 요약(summary)           | 필수                      | 문자열, 최대 200자                         | 목록 카드에 표시                                                                                                       |
| 카테고리(category)            | 필수                      | `erp` / `포트폴리오` / `쇼핑몰` 중 선택    |                                                                                                                        |
| 설명(description)             | 필수                      | 문자열                                     | 상세 페이지 설명                                                                                                       |
| 썸네일(thumbnail)             | 필수                      | 이미지 파일 업로드 (Supabase Storage)      | public 버킷에 업로드 후 반환된 공개 URL을 `thumbnail_url`로 저장                                                       |
| 프리뷰 이미지(preview_images) | 선택                      | 콤마 구분 문자열 → 배열 변환               | 코드만 제공하는 템플릿은 비워둘 수 있음. 이번 spec에서는 Storage 전환 대상이 아니며 기존 경로/URL 입력 방식을 유지한다 |
| 태그(tags)                    | 필수(1개 이상)            | 콤마 구분 문자열 → 배열 변환               |                                                                                                                        |
| 주요 기능(features)           | 필수(1개 이상)            | 콤마 구분 문자열 → 배열 변환               |                                                                                                                        |
| 사용 기술(tech_stack)         | 필수(1개 이상)            | 콤마 구분 문자열 → 배열 변환               |                                                                                                                        |
| 파일 목록(files)              | 필수(1개 이상, 최대 50개) | `file_path` + `code` 배열 (동적 추가/삭제) | `language`는 자동 추론, `sort_order`는 입력 순서                                                                       |

### 썸네일 업로드 (Supabase Storage)

- 썸네일은 텍스트 경로/URL 입력이 아니라 이미지 파일 업로드로 등록한다.
- 업로드 대상은 public 버킷이다 — 템플릿 조회 자체가 "누구나 조회 가능" 정책(RLS SELECT 공개)이므로 썸네일도 서명 URL 없이 공개 URL로 제공한다.
- 업로드가 완료되면 반환된 공개 URL을 기존 `thumbnail_url` 필드 값으로 사용한다(DB 컬럼/검증 스키마는 URL 문자열을 그대로 저장하므로 변경 없음).
- 프리뷰 이미지(preview_images)는 이번 spec의 Storage 전환 대상이 아니다. 기존과 동일하게 경로/URL 문자열 입력을 유지한다.
- 버킷 생성, RLS 정책, 업로드 API 등 실제 구현은 이번 문서의 범위가 아니며 다음 단계(PRD/구현)에서 진행한다.

### 배열 필드 입력 방식

태그·주요 기능·사용 기술·프리뷰 이미지는 콤마(,)로 구분한 문자열로 입력받고, 제출 시점에 문자열 배열로 변환한다.

### 파일 목록(files) 규칙

- 파일은 여러 개 등록할 수 있으며 동적으로 추가/삭제 가능하다(최대 50개).
- `file_path`: 상대 경로, `/`로 시작 불가, `\` 사용 불가, 최대 255자.
- `code`: 최대 100,000자.
- `language`: 사용자가 입력하지 않고 `file_path` 확장자에서 자동 추론한다.
- `sort_order`: 입력 순서를 그대로 표시 순서로 사용한다(알파벳순 아님).

## 경계 조건 / 검증

- 템플릿 내에서 `file_path`는 중복될 수 없다(폼 제출 전 클라이언트 검증 + 서버 UNIQUE 제약).
- 파일은 최소 1개, 최대 50개까지 등록 가능하다.
- 태그/주요 기능/사용 기술은 각각 최소 1개 이상 필요하다.
- 프리뷰 이미지는 없어도 등록 가능하다(선택).

## 에러 처리

- 파일 경로 중복 등록 시(서버 CONFLICT 응답): "이미 등록된 파일 경로가 있습니다" 메시지를 폼 상단에 표시한다.
- 그 외 API 에러는 서버에서 내려준 메시지를 그대로 표시한다.
- 폼 유효성 에러는 각 필드 하단에 인라인으로 표시한다.

## 권한

- 등록은 관리자만 가능하다(`requireAdmin` 가드).
- 관리자가 아닌 경우 403이 아닌 404를 반환한다 — 403은 "이 경로에 관리자 페이지가 존재한다"는 사실을 누설하므로 사용하지 않는다.
- 이 가드는 화면 노출 방지 목적이며 최종 방어선이 아니다. 실제 데이터 접근 통제는 DB의 RLS 정책이 담당한다.

## 기존 UI 패턴 재사용

- 폼: `FormField`(label/error/aria 자동 연결), `useAppForm` 공용 훅 재사용.
- 파일 반복 입력: `useFieldArray` 기반 `TemplateFileFieldArray` 패턴 재사용.
- 등록 성공 시 상세 페이지로 라우팅.

## Out of Scope (이번 spec 범위 아님)

- 카테고리 값 변경에 따른 실제 코드(`STARTER_KIT_CATEGORIES`, 스키마, mock 데이터, 필터 UI) 수정 — 다음 단계(PRD/구현)에서 진행.
- 썸네일 Storage 전환에 따른 실제 코드(Storage 버킷 생성, RLS 정책, 업로드 API, apiClient의 multipart 미지원 해소) 구현 — 다음 단계(PRD/구현)에서 진행.
- 프리뷰 이미지(preview_images)의 Storage 업로드 전환 — 이번 spec은 썸네일에 한정한다.
- 템플릿 상세 페이지의 코드 뷰어에 실제 렌더링(라이브 프리뷰) 기능 추가 — 별도 기능으로 분리해 이후 진행.
- 템플릿 수정/삭제 플로우(별도 spec 문서 `docs/templates/feature/update`, `docs/templates/feature/delete` 대상).
- 코드 문법 하이라이팅.
