# 랜딩페이지 PRD

## 개요

`/`(루트)에 Frontend Starter Platform의 메인 페이지를 구현한다. 텍스트 설명 → 데모 비디오
→ 북마크 수 기준 인기 템플릿 3개 캐러셀 순으로 구성되며, 채용 담당자/면접관이 빠르게
"무엇을 만들 수 있는 사람인가"를 파악할 수 있는 것을 목표로 한다. 모바일 퍼스트로
설계하고, SEO 메타데이터·비디오 접근성·초기 로딩 성능을 함께 고려한다.

## 사용자 스토리

1. 방문자로서, `/`에 진입하면 이 플랫폼이 무엇인지 텍스트로 먼저 파악하고 싶다.
2. 방문자로서, 스크롤하면 실제 사용 흐름(코드 복사 → 붙여넣기)을 비디오로 확인하고 싶다.
3. 방문자로서, 가장 많이 북마크된 인기 템플릿 3개를 캐러셀로 훑어보고 관심 있는 것의
   상세 페이지로 바로 이동하고 싶다.
4. 검색엔진/링크 공유를 통해 유입되는 방문자로서, 이 페이지가 무엇인지 미리보기(title,
   description, OG 이미지)로 알 수 있어야 한다.

## 기술 결정

### 인기 템플릿 조회: 신규 집계 함수 + 순수 CSS 캐러셀

**Context** — 랜딩페이지 캐러셀에 "북마크 수 기준 인기 템플릿 3개"를 보여줘야 한다.
기존 `getStarterKits()`(`src/features/starter-kit/api/get-starter-kits.ts`)는 `updated_at`
정렬만 지원하고 인기도 지표가 없다. 또한 캐러셀 UI를 만들 라이브러리가 프로젝트에
전혀 설치되어 있지 않다(embla, swiper 등 미설치, `src/components/ui`에도 carousel 없음).

**Decision**

- `bookmarks` 테이블(마이그레이션 `014_bookmarks.sql`)을 `target_type = 'template'` 기준으로
  `group by target_id`, `count(*) desc`, `limit 3` 집계하는 신규 함수를 추가한다
  (`getPopularStarterKits(limit: number)` — 위치는 `starter-kit/api` 또는 `bookmark/api`,
  Green 단계 시그니처 확정 시 결정). 집계된 `target_id`로 `templates` 테이블을 조회해
  `StarterKit[]`를 반환한다.
- `getStarterKits()`와 동일하게 Supabase 미설정 시 mock 데이터로 폴백한다
  (`isSupabaseConfigured()` 관례 재사용).
- 캐러셀 UI 자체(스와이프/자동 전환)는 신규 라이브러리를 추가하지 않고 CSS `scroll-snap`
  - 최소한의 JS(자동 전환 타이머, 좌우 이동 버튼)로 직접 구현한다.
- 스크롤 등장 애니메이션은 `gsap` + `@gsap/react`(`useGSAP`)를 신규 설치해 구현한다.
  적용 범위는 이번 랜딩페이지(`features/landing`)로 한정하며, 다른 도메인으로의 확장은
  이번 결정에 포함하지 않는다(§Alternatives 참고). `features/landing/ui`에 위치.

**Alternatives**

- **클라이언트 집계(안 B)**: 신규 API 없이 `getStarterKits()` 전체 결과를 받아와 북마크
  수를 매핑·정렬. API 변경이 없어 간단해 보이지만, 템플릿 수가 늘어날수록 불필요한
  페이로드와 클라이언트 연산이 증가하고, "인기순 상위 N개"라는 목적에 비해 우회적인
  방법이라 거부. DB 레벨 정렬이 성능·정확성 모두에서 명확히 우월하다.
- **캐러셀 라이브러리 도입(안 C)**: `embla-carousel-react` 등을 쓰면 스와이프 제스처·
  접근성 처리가 검증된 상태로 제공되지만, 이번이 프로젝트 내 캐러셀의 첫 사용처라
  CLAUDE.md의 "2회 규칙"(실제 두 번째 사용처가 재현될 때만 커널/의존성 승격)에 위배되고,
  "불필요한 라이브러리를 추가하지 않는다" 원칙과도 맞지 않아 거부. 캐러셀 자체의 전환
  로직은 라이브러리 없이도 충분히 구현 가능한 수준이라 판단.
- **스크롤 등장 애니메이션을 순수 `IntersectionObserver` + CSS transition으로 구현**:
  `terminal-hero.tsx`가 이미 순수 React state로 애니메이션을 구현한 선례가 있어 일관성은
  높으나, 스크롤 트리거 애니메이션(타임라인, 스태거, 이징 곡선 제어)을 여러 섹션(텍스트
  등장, 비디오 등장, 캐러셀 카드 순차 등장)에 걸쳐 손으로 구현하면 코드량과 버그 표면이
  늘어난다는 실무적 판단에 따라, 이번 이슈에 한해 `gsap`/`useGSAP` 사용을 채택했다.

**Consequences**

- 장점: DB 레벨 집계로 템플릿 수 증가에도 성능이 안정적이며, 기존 mock 폴백·조인 최소화
  관례를 그대로 따를 수 있어 코드베이스 일관성이 높다. gsap 도입으로 스크롤 등장
  애니메이션(타임라인, 스태거, cleanup)을 `useGSAP` 훅 하나로 선언적으로 작성할 수 있어
  구현 속도와 가독성이 좋아진다.
- 단점: 순수 CSS/JS 캐러셀은 라이브러리 대비 브라우저 호환성(구형 Safari의 `scroll-snap`
  세부 동작 차이)과 접근성(키보드 포커스 트랩, ARIA 롤 처리)을 직접 챙겨야 하는 부담이
  있다. `gsap`/`@gsap/react` 신규 의존성이 추가되며, 이번 랜딩페이지 1곳에서만 쓰여
  "2회 규칙" 관점에서는 아직 커널 승격 대상이 아니다 — 다른 도메인에서 유사 요구가
  재현되기 전까지는 `features/landing` 내부 의존성으로만 남긴다. `prefers-reduced-motion`
  처리는 gsap 타임라인 안에서 별도로 구현해야 한다(라이브러리가 자동 처리하지 않음).
  추후 캐러셀 사용처가 하나 더 생기면("2회 규칙" 충족 시) 자체 구현을 `shared/ui`로
  승격하거나 라이브러리 도입을 재검토해야 한다.
- 신규 집계 함수는 `bookmarks_target_idx` 인덱스(`target_type, target_id`)를 활용하지만,
  `group by + count` 쿼리 자체의 성능은 템플릿/북마크 규모가 커지면 별도 검증이 필요할 수
  있다(현재 규모에서는 문제없음).

## Out of Scope

- 데모 비디오 콘텐츠 자체의 녹화/편집 (정적 파일 업로드까지만 담당, 콘텐츠 제작은 별도)
- 캐러셀 호버 회전·패럴랙스 등 고급 인터랙션 (자동/수동 전환 + 스크롤 등장 애니메이션까지만)
- 비디오 자막 트랙 (콘텐츠 확정 전이라 이번 이슈에서 결정하지 않음)
- `/landing` 등 별도 라우트 신설 (기존 `/` 라우트를 그대로 사용)
- CTA 동선(전체 템플릿 보기 등 추가 유도 버튼) — 이번 스펙에서 다루지 않음
- 북마크 수 실시간 갱신 (페이지 로드 시점 스냅샷으로 충분, 실시간 구독 불필요)
- About 페이지, Starter/Feature 탐색 UI 확장 (routing.md상 별도 라우트, 이번 이슈 범위 아님)
