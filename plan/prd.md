# Frontend Starter Platform — PRD (Product Requirements Document)

**작성일**: 2026-08-04
**문서 성격**: 제품 요구사항 정의 (기술 설계는 [plan.md](./plan.md) 참조)
**작성 근거**: 1차 기획(Sonnet, UX/프론트엔드/백엔드/QA) + 2차 검토(Opus, 기획자/프론트엔드/백엔드/QA/AI 아키텍처)

---

## 1. 개요

### 1.1 제품명
Frontend Starter Platform

### 1.2 한 줄 정의
AI(Claude)와 함께 실무 프론트엔드 프로젝트를 빠르게 시작할 수 있도록, 디자인 시스템·컴포넌트·프로젝트 구조·문서·개발 규칙을 하나로 묶은 재사용 가능한 기반(Starter Platform).

### 1.3 배경 (Why)
포트폴리오/실무 프로젝트를 새로 시작할 때마다 비슷한 UI와 기능을 반복 구현해왔다. 프로젝트 내부적으로는 컴포넌트화를 해도, 새 프로젝트를 시작할 때마다 구조를 다시 잡고 컴포넌트를 옮겨와 수정하는 과정이 반복됐다. Claude 등 AI를 활용할 때도 매번 같은 컴포넌트·기능 생성을 요청하고, 생성된 코드를 프로젝트 구조에 맞춰 다시 손보는 데 많은 시간이 소요됐다.

이 문제의 해법은 "템플릿 하나 만들기"가 아니라, **디자인 시스템·프로젝트 구조·문서·개발 규칙·검증된 컴포넌트를 함께 관리**해 앞으로의 모든 프론트엔드 프로젝트가 딛고 설 수 있는 공통 기반을 만드는 것이다.

### 1.4 타겟 사용자 (Who)
- **1차(현재)**: 이 프로젝트를 만드는 본인 — 포트폴리오/실무 프로젝트를 반복적으로 시작하는 1인 프론트엔드 개발자
- **2차(잠재)**: 반응이 좋을 경우, 유사한 문제를 겪는 개발자 커뮤니티 (상용화는 4순위, 현재 범위 아님)

### 1.5 우선순위
1. 내가 사용할 Starter Platform 구축
2. 포트폴리오 완성
3. 지속적인 개선
4. 반응이 좋다면 상업화 검토

현재는 **상용 서비스가 목적이 아니다.** 모든 의사결정은 이 우선순위를 기준으로 한다.

## 2. 핵심 철학 & 원칙

### 2.1 핵심 철학
> **"반복 개발을 줄이는 것"**이 가장 중요한 목표다.

판단 기준은 "코드가 동작하는가"가 아니라 **"다음 프로젝트에서도 그대로 사용할 수 있는가"** 다.

우선 고려 사항: 재사용성 · 유지보수성 · 확장성 · 일관성 · 실무 활용성

### 2.2 AI 활용 철학
AI는 개발자를 대체하는 존재가 아니라, 반복 작업을 줄이고 생산성을 높이며 구현을 돕는 **협업 도구**다. 따라서 구현 시 다음을 항상 고려한다.
- AI가 이해하기 쉬운 구조
- AI가 수정하기 쉬운 구조
- 문맥(Context)이 명확한 구조

### 2.3 개발 원칙
- 구현보다 설계를 우선한다.
- 항상 "왜 필요한가?", "정말 재사용 가능한가?", "더 단순한 방법은 없는가?"를 먼저 고민한다.
- 필요 이상의 추상화를 하지 않는다 (YAGNI).
- 불필요한 라이브러리를 추가하지 않는다.
- 실무에서 사용할 수 있는 구조를 유지한다.

## 3. 목표와 성공 기준

### 3.1 제품 목표
"실무에서 사용할 수 있는 구조 + 재사용 가능한 컴포넌트 + 일관된 디자인 시스템 + 문서화 + AI 친화적 프로젝트 구조"를 갖춘 Frontend Starter Platform을 구축한다.

최종적으로 랜딩 페이지, 포트폴리오, 쇼핑몰, ERP, 관리자 페이지, 블로그 등 **다양한 프로젝트 유형에서 공통적으로 재사용 가능한 기반**이 되는 것이 목표다.

### 3.2 성공 기준 (측정 가능한 KPI)
- [ ] 첫 번째 프로젝트(포트폴리오) 적용 완료
- [ ] 두 번째 프로젝트에서 개발 시간 30% 이상 단축 (Starter 없는 경우 대비)
- [ ] 컴포넌트 재사용률 70% 이상
- [ ] 테스트 커버리지 `lib/hooks` 85% 이상
- [ ] AI(Claude)와 협업 시 컨텍스트 참조만으로 대부분의 요청 해결 (프롬프트 1회 반복 이내)

### 3.3 비목표 (Out of Scope, 현 단계)
- 상용 서비스로서의 배포/과금/멀티테넌시
- npm 패키지 배포, CLI 스캐폴딩 도구화 (§4.2 참조 — 반응 확인 후 검토)
- 커스텀 백엔드 서버 구축 (Route Handler를 BFF로만 사용)
- 크로스 브라우저 완전 대응, 시각적 회귀 테스트 자동화 (3차 이후로 후순위)

## 4. 요구사항 (Requirements)

### 4.1 기능 요구사항

#### FR-1. 디자인 시스템
- 색상 토큰을 Primitive → Semantic → Component 3계층으로 관리해야 한다.
- 라이트/다크 모드를 CSS 변수 기반으로 전환할 수 있어야 한다.
- 타이포그래피·스페이싱은 사전 정의된 스케일만 사용해야 한다 (커스텀 값 임의 추가 금지).

#### FR-2. 재사용 컴포넌트 라이브러리 (P0)
- shadcn/ui 기반 P0 컴포넌트 최소 12종(Button, Input, Form, Card, Dialog, Table, Dropdown-menu, Badge, Toast, Skeleton, Tabs, Avatar)을 제공해야 한다.
- 각 컴포넌트는 CVA로 variant/size API를 통일해야 한다.
- 모든 P0 컴포넌트는 편입 전 **Definition of Done 4개 기준**(타입 명시, 접근성, 반응형 3단계, 사용 예제 1개)을 충족해야 한다.

#### FR-3. 프로젝트 구조 및 재사용 메커니즘
- 단일 레포 구조로 `shared-kernel`(components/lib)과 `app`(도메인 코드)을 분리해야 한다.
- 새 프로젝트로의 이식은 **GitHub Template Repo 복제** 방식을 지원해야 한다 (npm 패키지·CLI 방식은 채택하지 않음).
- 코드가 커널로 승격되려면 **"2회 규칙"**(동일 요구가 2번째 프로젝트에서 재현될 때만 승격)을 충족해야 한다.
- `shared-kernel`과 `app` 간 의존은 단방향이어야 하며 ESLint로 강제해야 한다.

#### FR-4. 상태관리 및 폼 패턴
- UI 상태는 Zustand 슬라이스 팩토리로 표준화해야 한다.
- 서버 상태는 TanStack Query로 관리해야 한다 (캐싱/동기화 표준화).
- 폼은 React Hook Form + Zod 조합을 공통 훅(`useAppForm`)으로 얇게 래핑해야 한다.
- 공통 Zod 스키마(이메일, 전화번호 등)는 재사용 가능해야 한다.

#### FR-5. API 연동 및 백엔드 인터페이스
- Next.js Route Handler를 BFF로 사용해 인증 토큰을 httpOnly 쿠키로 관리해야 한다.
- API 에러는 `ApiError` 클래스와 공유 에러 코드 카탈로그(`types/api.ts`)로 표준화해야 한다.
- 환경변수는 Zod로 부팅 시점에 검증해야 한다.
- 개발/테스트용 목업은 Route Handler 기반으로 제공해야 한다 (MSW는 선택적 확장).

#### FR-6. AI 협업 구조
- 루트 및 주요 폴더에 `CLAUDE.md`를 배치해 로컬 컨텍스트를 제공해야 한다.
- 대표 사용 패턴은 `*.example.tsx` 또는 데모 페이지 형태로 제공해야 한다.
- 파일은 kebab-case, 컴포넌트/타입은 PascalCase, 변수/함수는 camelCase 네이밍을 일관되게 적용해야 한다.

#### FR-7. 품질 보증
- P0 컴포넌트는 7개 항목 체크리스트(렌더 스모크, Props 분기, 상호작용, 상태 경계, 접근성, 스타일 병합, 타입 안정성)를 통과해야 한다.
- Husky pre-commit에서 lint-staged(ESLint/Prettier)를 실행해야 하며, pre-push에서 타입체크와 변경분 테스트를 실행해야 한다.
- 접근성은 vitest-axe(컴포넌트 단위)와 eslint-plugin-jsx-a11y(린트 단계)로 자동 검증해야 한다.

### 4.2 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| **재사용성** | 컴포넌트/패턴은 최소 2개 이상의 프로젝트에서 수정 없이 또는 최소 수정으로 사용 가능해야 함 |
| **유지보수성** | 신규 참여자(또는 미래의 본인)가 CLAUDE.md만으로 구조를 파악할 수 있어야 함 |
| **확장성** | 새로운 프로젝트 유형(ERP, 쇼핑몰 등) 추가 시 커널 구조 변경 없이 `app/` 레벨 확장만으로 대응 가능해야 함 |
| **일관성** | 네이밍, 폴더 구조, 컴포넌트 API가 전체 프로젝트에서 동일한 패턴을 따라야 함 |
| **접근성** | 모든 P0 컴포넌트는 WCAG AA 기준(키보드 네비게이션, ARIA, 색 대비)을 충족해야 함 |
| **타입 안정성** | `any` 사용 금지, 모든 public API는 타입 export 필수 |
| **성능** | 불필요한 클라이언트 컴포넌트 남용 금지, 서버 컴포넌트 우선 원칙 준수 |

## 5. 사용자 시나리오 (User Scenarios)

### 시나리오 1 — 신규 프로젝트 시작
개발자가 새 포트폴리오 프로젝트를 시작한다. GitHub Template Repo를 복제하면 즉시 실행 가능한 프로젝트 뼈대(레이아웃, 인증 폼 예시, P0 컴포넌트, 린트/훅 설정)를 갖게 된다. 별도의 구조 설계 없이 바로 기능 개발에 착수한다.

### 시나리오 2 — AI와 협업한 기능 개발
개발자가 Claude에게 "로그인 폼을 만들어줘"라고 요청한다. Claude는 프로젝트의 `CLAUDE.md`와 `components/patterns/form-example.tsx`를 참조해, 기존 `useAppForm` 훅과 `loginSchema`를 재사용하는 코드를 생성한다. 별도의 구조 설명 없이도 프로젝트 컨벤션에 맞는 코드가 나온다.

### 시나리오 3 — 컴포넌트 재사용 여부 판단
두 번째 프로젝트(쇼핑몰)에서 동일한 형태의 상품 카드가 필요해진다. 첫 번째 프로젝트(포트폴리오)에서 이미 유사 컴포넌트가 있었다면 "2회 규칙"에 따라 공통 부분을 추출해 `shared-kernel`로 승격한다. 반대로 처음 등장하는 요구라면 해당 프로젝트의 `app/` 레벨에만 구현하고 커널에 넣지 않는다.

### 시나리오 4 — 디자인 토큰 변경
브랜드 컬러가 바뀌어 Semantic 토큰 값을 수정한다. 컴포넌트 코드는 하드코딩된 색상이 없으므로 CSS 변수만 교체하면 전체 프로젝트에 즉시 반영된다. 변경 후 P0 컴포넌트 쇼케이스 페이지에서 라이트/다크 모드를 육안으로 확인한다.

## 6. 범위 (Scope)

### 6.1 MVP 범위 (S1~S4, 7주)
- 프로젝트 기초 구조, 린트/훅 설정, CLAUDE.md 체계
- P0 컴포넌트 12종 + DoD 충족
- Zustand/TanStack Query/RHF+Zod 공통 패턴
- API 클라이언트, 인증 플로우(httpOnly 쿠키), 에러 표준화
- 포트폴리오 사이트에 병행 실적용 (검증 채널)

### 6.2 확장 범위 (S5~S7, 이후)
- 포트폴리오 완성 및 Starter 개선 피드백 반영
- P1 컴포넌트(DataTable, Sheet, Command, Pagination 등)
- Storybook/데모 페이지, GitHub Actions CI
- 문서화(README, 사용 가이드) 및 2차 프로젝트 적용

### 6.3 의도적으로 보류한 항목
- 시각적 회귀 테스트(Chromatic), Lighthouse CI — 3차 이후, 컴포넌트 안정화 후 도입
- 크로스 브라우저(Firefox/WebKit) 테스트 — 3차 이후
- 샘플 프로젝트는 3종이 아닌 **1종(포트폴리오)** 으로 축소 — 유지보수 비용이 본체를 초과한다는 QA·기획자 공통 판단
